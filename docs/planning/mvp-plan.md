# AI 금융사기 응급대응 비서 — 제출용 MVP 구현 기획서

## 1. 프로젝트 개요

### 프로젝트명

**AI 금융사기 응급대응 비서**

### 한 줄 설명

금융사기 의심 상황을 자연어로 입력하면 AI가 피해 정황을 구조화하고, 확인 질문과 규칙 엔진으로 현재 노출 상태를 판단하여 검증된 행동 지침을 우선순위대로 제공하는 웹서비스.

### 목표

2026 금융 AI Challenge에 실제 작동하는 MVP와 기능명세서를 제출한다.

본 서비스는 금융사기 여부를 확정하는 탐지기가 아니다. 사건이 진행 중인 금융소비자가 **현재 상태와 지금 해야 할 행동을 빠르게 이해하도록 돕는 응급대응 서비스**다.

> AI는 사용자의 말을 이해하고 구조화한다. 안전 판단과 행동 지침은 규칙 엔진과 출처가 확인된 지식베이스가 담당한다.

## 2. 해결하려는 문제

금융사기 의심 상황의 사용자는 다음 문제를 겪는다.

- 실제 금융사기인지 판단하기 어렵다.
- 이미 링크 클릭, 앱 설치, 정보 제공 또는 송금을 한 경우 무엇부터 해야 하는지 모른다.
- 공식 대응 정보가 여러 기관과 페이지에 흩어져 있다.
- 당황한 상태에서 긴 안내문을 읽고 행동의 우선순위를 정하기 어렵다.
- 요청받은 행동과 실제 수행한 행동을 혼동하거나 불명확하게 설명할 수 있다.
- 일반 생성형 AI는 출처가 불명확하거나 잘못된 행동 지침을 생성할 수 있다.
- 상담 과정에서 입력한 주민등록번호, 계좌번호 등 민감정보가 외부 AI로 전달될 수 있다.

본 서비스는 다음 방식으로 문제를 해결한다.

1. 자연어에서 위험 정황과 사용자 행동을 구조화한다.
2. 불명확한 핵심 행동은 사용자에게 다시 확인한다.
3. 단일 단계와 함께 기기·개인정보·인증수단·금전 피해 상태를 별도로 판단한다.
4. 공식 출처가 연결된 행동을 긴급도 순으로 제공한다.

## 3. 핵심 가치와 차별성

> 사기 가능성만 알려주는 것이 아니라, **피해를 더 키우지 않기 위해 지금 할 일을 알려준다.**

| 구분 | 검색·일반 안내 | 일반 생성형 AI | 본 서비스 |
|---|---|---|---|
| 상황 반영 | 사용자가 직접 탐색 | 가능하지만 비일관적 | 구조화 및 확인 질문 |
| 피해 상태 판단 | 사용자가 직접 판단 | 모델 답변에 의존 | 규칙 기반 다차원 판단 |
| 행동 우선순위 | 일반적 안내 | 답변마다 다를 수 있음 | 즉시·다음·보존 순 |
| 복합 피해 대응 | 여러 문서를 직접 조합 | 누락 가능 | 상태별 지침을 합성 |
| 공식 근거 | 문서별 제공 | 불확실할 수 있음 | 지침별 출처·확인일 |
| 민감정보 보호 | 서비스별 상이 | 원문 전송 가능 | 외부 전송 전 마스킹 |
| AI 장애 대응 | 해당 없음 | 답변 불가 | 고정 긴급 지침 제공 |

## 4. 주요 사용자와 대표 상황

### 주요 사용자

보이스피싱, 스미싱, 기관 사칭, 대출 사기, 지인 사칭 등이 의심되거나 이미 일부 행동을 수행한 일반 금융소비자.

고령층 등 디지털 취약 사용자를 고려하여 짧은 문장, 큰 버튼, 쉬운 표현을 우선한다.

### 대표 상황

- 의심 문자만 수신: 결제 문자를 받았으나 링크는 누르지 않음
- 기관 사칭: 검찰을 사칭하며 앱 설치를 요구함
- 복합 노출: 링크 클릭, 앱 설치, 개인정보 전달
- 금전 피해: 안전계좌라는 말에 돈을 송금함
- 불명확한 상황: “앱을 설치하라고 해서 확인해 봤다”처럼 수행 여부가 모호함

마지막 사례처럼 실제 행동 여부를 확정할 수 없으면 추가 질문을 표시한다.

## 5. MVP 목표와 성공 기준

### 사용자 목표

사용자는 서비스 진입 후 짧은 시간 안에 다음을 알 수 있어야 한다.

1. 어떤 위험 정황이 발견되었는가?
2. 기기·개인정보·인증수단·금전 측면에서 무엇이 노출되었는가?
3. 피해 확산을 막기 위해 지금 무엇부터 해야 하는가?

### 기능 성공 기준

- 자연어 입력과 샘플 시나리오 실행이 가능하다.
- 민감정보를 외부 LLM 전송 전에 마스킹한다.
- 요구받은 행동과 실제 수행한 행동을 구분한다.
- 부정 표현과 불확실한 상태를 구분한다.
- 핵심 상태가 불명확하면 확인 질문을 제공한다.
- 대표 단계와 다차원 노출 상태를 함께 판단한다.
- 모든 노출 상태에 필요한 행동을 누락 없이 조합한다.
- 지침별 공식 출처와 최종 확인일을 표시한다.
- LLM 장애 시에도 긴급 안내와 공식 확인 경로를 제공한다.
- 필수 심사 기간 동안 공개 URL이 정상 작동한다.

### 품질 목표

- 고위험 필수 행동 누락률: 0% 목표
- 규칙 엔진 및 지침 매핑 테스트 통과율: 100%
- 대표 자연어 평가 세트: 30~50건
- 행동 추출 성능: 항목별 precision, recall, F1 측정
- LLM 장애 시 fallback 안내 노출률: 100%

최종 기획서에는 임의 목표값이 아닌 실제 측정 결과를 제시한다.

- 진행 단계 시각화

- 쉬운 말 요약
- 고령층 접근성 모드

### P2 — 제출 이후 확장

- 문자 이미지 OCR
- 악성 URL 평판 조회
- 음성·녹취 분석
- 다국어 지원
- 최신 사기 유형 RAG
- 금융기관·신고 시스템 연동

### 현재 구현 현황 (2026-08-21)

- P0 핵심 흐름인 입력, 구조화 추출, 추가 확인, 규칙 판단, 행동 조합과 공개 배포를 구현했다.
- 추가 확인은 최대 3개 항목을 제출하며, 답변 후 선택지를 제거하고 결과 갱신을 알린다.
- `잘 모르겠음` 응답은 미확인 상태로 유지하되 현재 분석에서는 같은 질문을 반복하지 않는다.
- 추가 확인의 질문·답변을 결과에 짧게 남겨 판단 근거를 확인할 수 있다.
- 결과 상태는 확인됨·사용자 부정 확인·추가 확인 필요·언급 없음으로 구분한다.
- LEVEL 0은 확인된 피해가 없는 이유와 민감정보 마스킹·미확정 항목을 상황에 맞게 설명한다.
- 복합 상황의 모든 완료 행동을 독립적으로 추출하고 7개 노출 축에 동시에 반영한다.
- LLM 미연결·장애 시에도 로컬 규칙 추출기로 핵심 자연어와 복합 행동을 제한적으로 분석한다.
- 복합 피해 카드에 실질 피해 영역을 표시하고 영역별 공식 지침의 합집합을 제공한다.
- `앱 설치·인증정보·송금 복합 피해`를 포함한 7개 샘플과 자동 테스트 70개를 운영한다.
- 인젝션성 지시와 실제 피해 행동이 함께 있어도 피해 행동과 대응 지침이 누락되지 않는지 회귀 테스트한다.
- 사용자·공격자·제3자 주체, 현재·과거 사건, 요구·거절, 구어체와 정정·모순·가정·사후 조치·부분 제공 CASE 1~50을 별도 회귀 데이터로 관리한다.
- 초기·결과·추가 확인·복합 피해 화면의 Streamlit 렌더링 검증을 완료했다.

## 7. 상세 기능 명세

### F01. 고정 긴급 안내

LLM 분석 여부와 관계없이 첫 화면 상단에 표시한다.

```text
이미 돈을 송금했다면 분석을 기다리지 말고 금융회사에 즉시 피해 사실을 알리세요.
상대방이 설치하도록 한 앱이 있다면 해당 기기에서 금융·인증 앱 사용을 중단하세요.
상대방과 통화 또는 화면 공유 중이라면 먼저 연결을 종료하세요.
```

연락처와 기관 정보는 공식 자료로 확인한 값만 표시하며 출처와 확인일을 관리한다.

### F02. 자연어 입력

입력창에 다음 주의를 표시한다.

> 주민등록번호, 계좌번호, 카드번호, 비밀번호, 인증번호를 입력하지 마세요.

빈 입력, 지나치게 짧은 입력과 최대 길이 초과를 검증한다.

### F03. 민감정보 탐지 및 마스킹

외부 LLM 호출 전에 로컬 코드로 다음 정보를 마스킹한다.

- 주민등록번호, 전화번호, 카드번호 형식
- 계좌번호로 추정되는 긴 숫자열
- 이메일 주소
- 인증번호 또는 비밀번호로 명시된 값

```text
입력: 계좌번호는 123-456-789012이고 인증번호 839201을 알려줬어요.
전송: 계좌번호는 [계좌번호 마스킹]이고 인증번호 [인증정보 마스킹]을 알려줬어요.
```

마스킹이 발생하면 실제 값을 다시 표시하지 않고 감지된 정보 유형과 외부 전송 전 로컬 처리 사실을 안내한다. 마스킹은 완전한 탐지를 보장하지 않으므로 입력 금지 안내를 함께 제공한다. 원문과 결과는 서버·애플리케이션 로그나 DB에 저장하지 않는다.

### F04. AI 구조화 추출

LLM은 최종 판단과 행동 지침을 생성하지 않고 사실 후보를 구조화한다.

추출은 문장을 바로 피해 상태로 바꾸지 않고 `행동 주체 → 행동 종류 → 실제 수행 여부 → 현재 사건 여부 → 모순 여부`를 확인한다. 가족·친구 등 제3자의 행동은 사용자 노출로 올리지 않으며, 과거 사건과 현재 사건이 함께 있으면 현재 사건의 명시 상태를 우선한다. 상대방의 요구 후 사용자 거절이 확인되면 최종 행동 상태는 `denied`다. 중요 피해 행동에 서로 충돌하는 진술이 있으면 마지막 표현을 임의로 채택하지 않고 `unknown`으로 정규화한 뒤 추가 질문으로 재확인한다. MVP 기간에는 상위 행동 축을 유지하되, 한 축 안의 세부 정보별 제공·미제공 사실은 `evidence`에 독립적으로 보존한다. 본격 앱에서는 `account_info_shared`, `card_info_shared`, `password_shared`, `auth_secret_shared`와 같은 세부 행동 축으로의 확장을 검토한다.

배포 환경에 API 키가 있으면 LLM Structured Outputs를 우선 사용한다. API 키가 없거나 호출이 실패하면 로컬 규칙 추출기가 핵심 행동별 수행·요구·부정·불명확 상태를 독립적으로 판정한다. 로컬 분석은 범위가 제한된 보조 경로이며 화면에 사용 사실을 표시한다. 두 경로 모두 민감정보를 먼저 마스킹하고 동일한 데이터 모델 검증과 규칙 엔진을 통과한다.

각 행동 상태는 다음 중 하나다.

- `done`: 사용자가 수행함
- `requested`: 상대방이 요구했으나 수행 여부 불명
- `denied`: 수행하지 않았다고 명시함
- `unknown`: 문장만으로 판단 불가
- `not_mentioned`: 언급 없음

```json
{
  "impersonated_entity": "검찰",
  "risk_signals": ["수사기관 사칭", "범죄 연루 공포 유발", "앱 설치 요구"],
  "actions": {
    "suspicious_contact_received": {
      "status": "done",
      "evidence": "검찰이라고 전화가 왔고"
    },
    "link_clicked": {"status": "not_mentioned", "evidence": null},
    "app_installed": {
      "status": "requested",
      "evidence": "앱을 설치하라고 합니다"
    },
    "remote_control_enabled": {"status": "not_mentioned", "evidence": null},
    "personal_info_shared": {"status": "not_mentioned", "evidence": null},
    "financial_info_shared": {"status": "not_mentioned", "evidence": null},
    "auth_secret_shared": {"status": "not_mentioned", "evidence": null},
    "money_transferred": {"status": "not_mentioned", "evidence": null}
  }
}
```

서버에서 JSON Schema 또는 데이터 모델 검증을 수행한다. 값·필드가 잘못되거나 파싱에 실패하면 결과를 신뢰하지 않고 F11로 전환한다.

### F05. 추가 확인 질문

다음 조건에서 확인 질문을 표시한다.

- 핵심 행동이 `requested` 또는 `unknown`
- 입력의 모순 표현이 `unknown`으로 정규화됨

`done`, `denied`, `not_mentioned` 상태에는 질문을 만들지 않는다. 따라서 사용자가 앱 설치나 송금을 명시적으로 수행했다고 말한 경우 동일 항목을 다시 묻지 않는다. 우선 확인 대상은 통화·화면 공유, 링크 클릭, 앱 설치·원격제어, 개인정보·신분증, 금융·인증정보, 송금·현금 전달이다.

선택지는 `예`, `아니오`, `잘 모르겠음`, `해당 없음`으로 한다. 현재 판단에 중요한 질문을 최대 3개까지 보여준다. 모든 항목에 명시적으로 답해야 반영하며, 제출 후 질문 영역을 닫고 결과 갱신 완료 메시지를 표시한다. `잘 모르겠음`은 미확인 상태로 유지하되 현재 분석에서는 같은 질문을 반복하지 않는다.

### F06. 다차원 피해 상태 판단

하나의 LEVEL로 상태를 덮어쓰지 않고 다음 축을 별도로 유지한다.

| 상태 축 | 예시 |
|---|---|
| 접촉 | 의심 연락, 통화 중, 화면 공유 중 |
| 링크·웹 | 클릭, 사이트 접속, 정보 입력 |
| 기기 | 앱 설치, 원격제어, 과도한 권한 |
| 개인정보 | 주민등록정보, 주소, 신분증 |
| 금융정보 | 계좌, 카드, 비밀번호 |
| 인증수단 | 인증번호, 공동인증서, 보안매체 |
| 금전 피해 | 송금, 현금·상품권 전달 |

```json
{
  "contact_active": false,
  "web_exposure": ["link_clicked"],
  "device_exposure": ["app_installed"],
  "personal_data_exposure": ["id_number_shared"],
  "financial_data_exposure": ["account_number_shared"],
  "authentication_exposure": [],
  "financial_loss": []
}
```

행동 지침은 모든 상태의 합집합을 기반으로 생성한다.

두 개 이상의 실질 피해 영역이 확인되면 복합 피해로 판단한다. 단순 의심 연락은 복합 피해 개수에서 제외한다. 예를 들어 앱 설치·개인정보 제공·송금이 함께 확인되면 `기기`, `개인정보`, `금전 피해` 3개 영역을 모두 표시하고, 지급정지·악성 앱 조치·개인정보 노출 등록·증거 보존 지침을 함께 제공한다.

### F07. 대표 피해 단계

| 단계 | 표시명 | 대표 조건 |
|---|---|---|
| LEVEL 0 | 정보 부족·일반 상담 | 위험 정황 판단이 어려움 |
| LEVEL 1 | 의심 연락·요구 | 의심 연락 수신, 위험 행동 미수행 |
| LEVEL 2 | 링크·웹 노출 | 의심 링크 클릭·사이트 접속 |
| LEVEL 3 | 기기 노출 | 앱 설치·원격제어·권한 허용 |
| LEVEL 4 | 정보·인증 노출 | 개인정보·금융정보·인증수단 전달 |
| LEVEL 5 | 금전 피해 | 송금·현금·상품권 전달 |

가장 높은 단계는 **사용자용 상황 요약**에만 사용한다. 행동 결정은 F06의 모든 상태를 사용한다.

LEVEL 0은 안전하다는 뜻이 아니다.

> 현재 입력만으로 위험 상태를 판단하기 어렵습니다. 금융사기가 아니라는 의미는 아니며 공식 채널을 통해 별도로 확인하세요.

### F08. 공식 지침 기반 행동 조합

지침은 LLM이 생성하지 않는다. 공식 자료 기반 지식베이스에서 상태별 행동을 조회하고 중복을 제거한다.

1. `IMMEDIATE`: 지금 즉시 할 일
2. `NEXT`: 즉시 조치 후 할 일
3. `EVIDENCE`: 증거 보존
4. `PREVENTION`: 추가 피해 예방

```json
{
  "action_id": "DEVICE_EXPOSURE_01",
  "title": "노출 가능 기기에서 금융거래 중단",
  "instruction": "상대방이 설치하도록 한 앱이 있는 기기에서는 금융·인증 앱 사용을 중단하세요.",
  "applies_when": ["app_installed", "remote_control_enabled"],
  "priority": "IMMEDIATE",
  "source_title": "공식 자료명",
  "source_url": "https://official.example/replace-before-release",
  "issuing_authority": "발행 기관",
  "verified_at": "2026-08-20"
}
```

개발 중 공식 자료를 조사해 예시 값을 실제 문구와 URL로 교체한다. 출처·적용 조건·우선순위·확인일이 없는 지침은 배포하지 않는다.

### F09. 결과·근거·출처 표시

결과 화면의 표시 순서는 다음과 같다.

1. 지금 즉시 할 행동
2. 대표 피해 단계
3. 확인된 다차원 노출 상태
4. 감지된 위험 신호와 입력 근거
5. 다음 행동과 증거 보존
6. 공식 출처
7. 불확실하거나 추가 확인이 필요한 항목

서비스는 “금융사기가 확실하다” 또는 “안전하다”고 단정하지 않는다.

### F10. 샘플 시나리오

- 의심 문자를 받았지만 링크를 누르지 않음
- 택배 문자 링크를 클릭함
- 검찰 사칭 상대가 보낸 앱을 설치함
- 가족 사칭 메시지에 개인정보를 전달함
- 대출 빙자 사기에 송금함
- 앱 설치 여부가 모호하여 확인 질문이 필요함
- 앱 설치·개인정보 제공·송금이 함께 발생한 복합 피해

각 샘플의 기대 상태와 기대 행동을 정의해 시연과 자동 테스트에 함께 사용한다.

### F11. 오류·장애 시 안전한 대체 안내

LLM 시간 초과·한도 초과, API 키 누락, 잘못된 구조화 출력, 무관·모순 입력, 네트워크 오류를 처리한다. API 키가 없거나 LLM 호출이 실패하면 로컬 규칙 분석으로 전환하고 사용자에게 분석 방식과 한계를 알린다.

```text
AI 연결이 원활하지 않아 로컬 규칙으로 분석했습니다.
불명확한 항목은 추가 질문과 공식 채널을 통해 확인하세요.
[로컬 분석 결과]
[고정 긴급 행동]
[공식 확인 경로]
```

사용자 입력은 데이터로만 취급하며, 입력 안의 명령이 시스템 규칙이나 출력 스키마를 바꾸지 못하도록 프롬프트와 검증 로직을 구성한다.

### F12. 테스트 및 공개 배포

- 공개 URL에서 로그인 없이 핵심 시나리오를 실행한다.
- 비밀키는 저장소가 아닌 배포 환경 변수로 관리한다.
- 로그에 사용자 원문과 민감정보를 남기지 않는다.
- 일일 배포 점검 절차를 마련한다.
- URL은 **2026-09-07 11:00~2026-09-11 23:59** 동안 반드시 접근 가능해야 한다.

## 11. 안전 및 개인정보 원칙

### 단정 제한

“안전하다”라고 판단하지 않는다. 정보가 부족하면 판단 한계와 공식 확인 필요성을 알린다.

### 공식 자료 우선

경찰청, 금융감독원, 금융위원회, 금융보안원 및 관련 기관의 공식 자료를 기반으로 지침을 작성한다. 출처가 없거나 최신성을 확인하지 않은 지침은 배포하지 않는다.

### 데이터 최소화

- 회원가입과 불필요한 개인정보를 받지 않는다.
- 외부 전송 전 민감정보를 마스킹한다.
- 입력과 결과를 DB 및 로그에 저장하지 않는다.
- 사용하는 LLM 제공자의 데이터 처리 정책을 기획서에 명시한다.

### 환각·프롬프트 인젝션 통제

- LLM은 제한된 스키마만 출력한다.
- 서버에서 타입과 허용값을 검증한다.
- 입력 안의 명령을 시스템 지시로 해석하지 않는다.
- 행동 문구·연락처·출처는 LLM 출력에서 사용하지 않는다.
- 검증 실패 시 fallback으로 전환한다.

### 한계 고지

본 서비스는 공식 신고기관이나 금융회사를 대체하지 않으며 입력 내용에 기반한 대응 보조 도구임을 명시한다.

## 14. 테스트 및 평가

### 필수 시나리오

1. 문자만 받고 링크를 누르지 않음
2. 링크 클릭 후 정보는 입력하지 않음
3. 앱 설치 요구를 받았지만 설치하지 않음
4. 앱을 실제 설치함
5. 앱 설치 여부가 불명확함
6. 개인정보만 제공함
7. 인증번호만 제공함
8. 링크 없이 전화로 송금함
9. 앱 설치와 개인정보 제공이 동시에 발생함
10. 앱 설치·인증정보 제공·송금이 모두 발생함
11. “설치할 뻔했지만 하지 않았다” 같은 부정 표현
12. 무관한 일반 금융 질문
13. 민감한 번호가 포함된 입력
14. LLM 시간 초과 및 잘못된 JSON
15. 모델 지시를 바꾸려는 문장이 포함된 입력

각 테스트는 기대 행동 상태, 대표 단계, 반드시 포함할 지침 ID를 가진다.

