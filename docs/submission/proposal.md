## 1. 해결하려는 문제

금융사기 의심 상황에 놓인 사용자는 짧은 시간 안에 여러 결정을 내려야 한다. 그러나 기존
정보는 기관별로 흩어져 있고, 사용자는 자신이 링크만 눌렀는지, 앱까지 설치했는지,
개인정보나 인증번호를 전달했는지, 송금까지 했는지를 스스로 분류해야 한다. 피해 직후에는
긴 설명을 읽거나 적절한 검색어를 고르는 것조차 어렵다.

특히 실제 피해는 한 단계로만 나타나지 않는다. 링크 클릭, 악성 앱 설치, 화면 공유,
개인정보·금융정보·인증정보 제공, 송금이 한 사건에서 동시에 발생할 수 있다. 가장 높은 위험
단계만 보여주면 다른 노출 영역의 필수 조치가 누락될 수 있다. 반대로 민감정보가 문장에
등장했다는 이유만으로 사용자가 그 정보를 사기범에게 제공했다고 판단하면 과잉 안내와
불필요한 질문이 발생한다.

이 서비스는 다음 세 가지 문제를 해결한다.

1. 사용자의 자연어 설명에서 **누가, 무엇을, 실제로 했는지**를 분리한다.
2. 여러 피해 상태를 동시에 보존해 필요한 공식 대응을 빠짐없이 조합한다.
3. 분석을 기다리기 전에 송금·악성 앱 등 긴급 상황의 우선 행동을 먼저 보여준다.

## 2. 제안 서비스

사용자가 의심 상황을 짧게 입력하면 서비스는 민감정보를 로컬에서 먼저 마스킹한다. 이후
OpenAI Responses API의 `gpt-5.6-luna`와 Pydantic Structured Outputs로 행동 사실만
제한된 스키마에 맞춰 추출하고, 규칙 엔진으로 노출 상태와 대표 LEVEL을 계산한다. 결과
화면은 위험 점수보다 **지금 즉시 할 일**을 먼저 보여주며, 모든 행동지침에 공식 출처와
확인일을 붙인다. API 키가 없거나 호출이 실패하면 로컬 규칙 분석기로 안전하게 전환한다.

### 대상 금융소비자와 서비스 채널

| 구분 | 설계 반영 |
|---|---|
| 핵심 사용자 | 보이스피싱·스미싱·기관 사칭 연락을 받은 금융소비자와 가족 피해를 대신 확인하는 보호자 |
| 사용자 상태 | 불안·시간 압박으로 긴 설명과 복잡한 메뉴 탐색이 어려운 상황 |
| 1차 채널 | 설치와 로그인 없이 접근하는 모바일·데스크톱 반응형 웹 |
| 입력 방식 | 기억나는 사실을 짧은 자연어로 입력하고 불명확한 항목만 추가 확인 |
| 출력 방식 | 즉시 행동을 먼저 표시하고 공식 기관·URL·확인일을 함께 제공 |
| 확장 채널 | 금융회사 앱 내 WebView·상담원 보조 화면·이상거래 알림 후속 링크 |

MVP는 특정 연령이나 금융 이해도를 전제로 하지 않는다. 입력 항목을 금융 용어 중심의
설문으로 고정하지 않고 자연어와 최소 질문을 사용해 디지털 금융 취약 사용자도 핵심 대응
순서를 빠르게 확인하도록 설계했다.

### 핵심 사용자 흐름

```text
서비스 진입 → 고정 긴급 안내
  ↓
자유 입력 또는 7개 샘플 선택
  ↓
가족·지인 언급 시 분석 대상 명시 선택
  ↓
민감정보 로컬 마스킹
  ↓
OpenAI 구조화 추출 또는 로컬 fallback
  ↓
불명확한 행동만 최대 3개 추가 확인
  ↓
다차원 노출 상태 + 대표 LEVEL 계산
  ↓
지금 즉시 할 일 → 다음 행동 → 증거 보존 → 공식 출처
```

### 행동 상태 모델

| 상태 | 의미 | 추가 질문 |
|---|---|---|
| `done` | 사용자가 실제로 수행함 | 하지 않음 |
| `denied` | 사용자가 하지 않았다고 명시함 | 하지 않음 |
| `requested` | 상대방이 요구했으나 수행 여부는 불명 | 필요 시 질문 |
| `unknown` | 수행 행동을 언급했지만 기억·진술이 불확실함 | 질문 |
| `not_mentioned` | 사용자 수행 행동 자체가 언급되지 않음 | 보통 질문하지 않음 |

예를 들어 “문자에 내 계좌번호가 적혀 있었다”는 금융정보가 문자의 내용에 존재한다는
진술이지, 사용자가 계좌번호를 제공했다는 진술이 아니다. 이 경우 맥락은 evidence로
보존하되 `financial_info_shared=not_mentioned`로 처리한다.

## 3. 핵심 차별점

### 3.1 AI와 안전 판단의 역할 분리

본 서비스는 “AI가 금융사기를 확정한다”고 주장하지 않는다. AI 또는 로컬 추출기는 기관,
위험 신호, 행동과 수행 상태 등 **사실 후보를 제한된 스키마로 구조화**한다. 최종 노출 상태,
대표 LEVEL, 추가 질문, 행동 우선순위와 공식 지침 조합은 검증 가능한 규칙 엔진이 수행한다.

이 구조는 생성형 AI가 연락처나 신고 절차를 임의로 만들어내는 위험을 줄인다. 행동 문구,
기관명, URL과 확인일은 버전 관리되는 공식 지침 저장소에서만 가져온다.

### 3.2 복합 노출을 잃지 않는 다차원 판단

서비스는 접촉, 링크·웹, 기기, 개인정보, 금융정보, 인증수단, 금전 피해의 7개 축을 독립적으로
유지한다. 대표 LEVEL은 사용자가 상황을 한눈에 이해하도록 가장 높은 단계만 요약하지만,
행동지침은 모든 활성 노출 축의 합집합으로 구성한다.

예를 들어 앱 설치·인증번호 제공·송금이 함께 확인되면 LEVEL 5만 표시하고 끝내지 않는다.
지급정지·112 신고, 악성 앱 점검, 인증수단 폐기·재발급 확인, 피해 증빙 보존을 함께 안내한다.

### 3.3 부정·불확실·미언급을 구분하는 질문 정책

“설치하지 않았다”는 `denied`, “설치했는지 기억이 안 난다”는 `unknown`, 앱 설치 행동을
아예 말하지 않은 경우는 `not_mentioned`다. 확정된 `done`·`denied` 항목을 다시 묻지 않고,
`requested`·`unknown`·모순 상태만 확인해 피해 상황의 사용자가 불필요한 질문을 반복해서
받지 않도록 했다.

### 3.4 외부 전송 전 로컬 마스킹

주민등록번호, 전화번호, 이메일, 카드번호, 계좌번호, 인증번호와 비밀번호를 외부 분석 전에
로컬에서 치환한다. 단순 숫자 패턴만 지우지 않고 날짜·시간·금액·사건번호·주문번호 등 사건
판단에 필요한 정보는 보존하도록 문맥 기반 평가를 수행했다.

### 3.5 정보 우선순위 중심 UI

- 빨강: 즉시 행동
- 노랑: 주의·추가 확인
- 파랑: 안내·공식 근거
- 결과 최상단: 위험 점수가 아니라 `지금 즉시 할 일`
- 긴 문장 대신 상태 카드, 행동 카드와 출처 카드로 분리

### 3.6 기존 방식과의 차이

| 방식 | 한계 | 본 서비스의 보완 |
|---|---|---|
| 기관별 FAQ·검색 | 사용자가 피해 유형과 검색어를 먼저 알아야 함 | 자연어에서 수행 행동을 추출해 필요한 지침만 조합 |
| 일반 생성형 챗봇 | 행동지침·연락처 생성 오류와 판단 근거 불명확 | AI는 사실 추출만 수행하고 지침은 검증 저장소에서 제공 |
| 단일 위험 점수 | 복합 피해에서 낮은 단계의 필수 조치가 누락될 수 있음 | 7개 노출 축을 보존해 모든 필수 행동을 합성 |
| 고정 체크리스트 | 미언급·거절·불확실 상태를 구분하기 어려움 | 행동별 상태 모델과 선택적 추가 질문 적용 |

## 5. 시스템 구조

```text
Streamlit UI
  ↓
Privacy Filter
  └─ 주민번호·전화·이메일·카드·계좌·인증번호·비밀번호 로컬 마스킹
  ↓
Structured Extractor
  ├─ OpenAI Responses API + gpt-5.6-luna + Pydantic Structured Outputs
  ├─ 응답 저장 비활성화, 20초 timeout, 애플리케이션 최대 2회 시도
  └─ 키 누락·호출·검증 실패 시 Local Korean Rule Extractor
  ↓
Schema Validator
  ↓
Question Engine + Deterministic Rule Engine
  ↓
Verified Guide Store
  ↓
Result Composer
  └─ 즉시 행동·다음 행동·증거 보존·공식 출처
```

현재 배포는 Streamlit secret의 `OPENAI_API_KEY`를 최상위 환경 변수로 주입해 OpenAI
구조화 추출을 우선 사용한다. 외부 전송 전에 민감정보를 마스킹하고 API 응답 저장은
비활성화한다. 실제 LLM 문맥 50건 평가는 아직 실행하지 않았으므로 아래 자연어 성능은
로컬 규칙 분석기의 고정 회귀 결과로만 제시한다. API 성공 여부와 무관하게 스키마 검증,
결정론적 규칙 판단, 공식 지침 조합과 고정 긴급 안내는 동일하게 유지한다.

## 7. 검증 결과

### 7.1 평가 자산

| 평가 자산 | 사례 수 | 목적 |
|---|---:|---|
| 기존 범주형 자연어 평가 | 45건 | 15개 범주의 초기 baseline과 취약 유형 확인 |
| 제출용 문맥 회귀 평가 | 50건 | 피드백 반영 후 주체·시간·부정·정정·복합 상황 회귀 검증 |
| 합성 마스킹 평가 | 70건 | 7개 민감정보 유형과 오탐·보존성 검증 |
| 은행 계좌번호 문맥 평가 | 63건 | 은행명 문맥과 다양한 계좌번호 표기 검증 |
| 제출용 통합 마스킹 평가 | 133건 | 합성 70건과 계좌번호 63건의 통합 결과 |

초기 45건과 제출용 50건은 서로 다른 데이터셋이므로 직접 향상률로 계산하지 않는다. 초기
45건 baseline은 행동 상태 정확도 89.17%, 대표 LEVEL 정확도 82.22%를 기록했다. 이후 실패
유형을 반영해 별도 문맥 회귀 50건을 구축했고 현재 제출 기준 로컬 결과는 50/50이다.

### 7.2 제출용 문맥 회귀 50건

| 지표 | 실측 결과 |
|---|---:|
| 사례 통과율 | 100% (50/50) |
| 행동 상태 정확도 | 100% (128개 라벨) |
| 노출 정확도 | 100% (128개 라벨) |
| 대표 LEVEL 정확도 | 100% (50건) |
| 필요 질문 정확도 | 100% (7개 라벨) |
| 금지 질문 발생률 | 0% (0/117) |

### 7.3 통합 마스킹 133건

| 지표 | 실측 결과 |
|---|---:|
| 사례 통과율 | 100% (133/133) |
| 민감정보 탐지 성공률 | 100% (141/141) |
| 민감정보 누락률 | 0% (0/141) |
| 과잉 마스킹률 | 0% (0/704) |
| 복합 민감정보 사례 통과율 | 100% (10/10) |

### 7.4 행동지침 독립 라벨

고위험 대표 12건에 자동 파생이 아닌 독립 라벨을 부여했다. 필수 지침 33개는 모두
출력됐고, 발생하면 안 되는 금지 지침 48개는 한 건도 출력되지 않았다.

### 7.5 소프트웨어 검증

- pytest 자동 테스트 101개 통과
- 전체 `src` 커버리지 90%, 로컬 자연어 추출기 커버리지 100%
- OpenAI Responses API 요청 계약, Structured Outputs 파싱과 장애 fallback 단위 테스트 통과
- Ruff 정적 검사 통과
- 공개 URL의 비로그인 접근과 실제 API 1건 호출은 제출 전 배포 환경에서 최종 확인

### 7.6 API 배포 검증 기준

샘플 모드는 사전 정의 결과를 사용하므로 API 검증에 사용하지 않는다. 배포 환경에서
개인정보가 없는 문장을 **직접 입력**하고 다음 항목을 확인한다.

- 성공 시 “AI 분석이 완료되었습니다.”와 구조화 응답 검증 안내 표시
- 장애 시 로컬 fallback 안내와 고정 긴급 행동 유지
- OpenAI Platform Usage에서 같은 시각의 호출 확인
- 시크릿 브라우저에서 로그인 없이 공개 URL 접근

세부 절차는 [OpenAI API 동작 확인 가이드](../api-verification.md)에 기록한다. 현재 URL은
인증 페이지로 리디렉션되므로 Streamlit 공개 범위 설정을 제출 전에 해제·재검증해야 한다.

## 8. 안전·신뢰 설계

- 금융사기 여부와 안전 여부를 단정하지 않는다.
- 송금 피해·악성 앱 관련 고정 안내는 분석 성공 여부와 무관하게 표시한다.
- 사용자 입력을 시스템 명령이 아닌 데이터로만 취급한다.
- 행동지침을 LLM이 생성하지 않고 공식 자료 저장소에서만 가져온다.
- 사용자 원문과 결과를 DB·파일·애플리케이션 로그에 저장하지 않는다.
- `.env`, Streamlit secrets와 API 키는 Git 추적 대상에서 제외한다.
- 금융위원회, 한국인터넷진흥원, 경찰청 공식 URL과 112·118·1332 연락처를
  2026-08-24에 확인했다.
- API 키는 Streamlit secret 또는 로컬 환경 변수로만 주입하고 저장소 파일에 포함하지 않는다.
- 외부 API에는 로컬 마스킹된 문자열만 전송하고 Responses API의 응답 저장을 비활성화한다.
- OpenAI SDK 내부 재시도는 끄고 20초 timeout과 최대 2회 애플리케이션 시도로 장애 시간을
  제한한 뒤 로컬 분석으로 전환한다.

## 9. 서비스 한계

- OpenAI 구조화 추출을 우선 사용하지만 실제 LLM 문맥 50건 평가는 아직 완료하지 않았으므로
  로컬 회귀 성능을 LLM 성능으로 표현하지 않는다. API 장애 시 사용되는 로컬 규칙 분석기도
  모든 현실 표현을 이해한다고 보장하지 않는다.
- LEVEL은 확률이나 법적 판단이 아니라 확인된 행동 중 가장 높은 대응 단계를 요약한 값이다.
- 마스킹은 합성 평가 세트에서 검증했지만 모든 현실 입력의 완전 탐지를 보장하지 않으므로
  입력 전 민감정보 작성 금지 안내를 함께 제공한다.
- 본 서비스는 금융회사, 수사기관과 공식 신고기관을 대체하지 않는 대응 보조 도구다.
- 자동 지급정지, 신고 접수, 계좌·기기 직접 제어는 수행하지 않는다.

## 11. 기대 효과

사용자는 금융사기 지식을 직접 검색하고 분류하지 않아도 자신의 행동 사실을 입력해 현재
노출 상태와 행동 순서를 확인할 수 있다. 금융회사와 공식 기관에는 피해자가 “무엇을 했는지”를
구조화해 설명할 수 있는 출발점을 제공한다. 공모전 MVP는 생성형 AI의 유연성과 결정론적
규칙·공식 지침의 신뢰성을 분리해, 실제 금융소비자 보호 서비스로 확장 가능한 안전 구조를
검증한다.
